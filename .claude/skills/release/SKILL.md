# Release visor-cli

A pushed `v*` tag runs `.github/workflows/release.yml` (generated by dist): it
builds 5 targets, creates the GitHub release with the shell and PowerShell
installers, and commits `Formula/visor.rb` to `Visor-Finance/homebrew-tap`.
This skill covers what dist does not: picking the version, the notes, and
checking the result.

Stop and report at the first failing step. Never delete or move a pushed tag;
fix forward with a new patch version.

## 1. Start clean

```bash
git switch main && git pull --ff-only
git status --short          # must be empty
gh run list --branch main --workflow CI --limit 1   # last CI must be green
```

## 2. Sync the API spec

```bash
scripts/sync-openapi.sh --remote     # or with no argument from ../visor
cargo test --test contract
```

If the spec changed and the contract test fails, the release is blocked: the
API gained or changed operations. Implement them first (see `AGENTS.md`),
then start over. If the spec changed and the test passes, commit it:
`Sync the personal API spec`.

## 3. Choose the version

List what ships: `git log --oneline $(git describe --tags --abbrev=0)..HEAD`.
Nothing user-visible means no release.

The public contract is the command and flag names, `--json` output (the API
body), exit codes, environment variables, and the config and credential
locations. While the version is `0.x`:

| Change | Bump |
|---|---|
| Breaks the contract: removes or renames a command or flag, changes an exit code or a default | minor (`0.1.3` → `0.2.0`) and a **Breaking** line in the notes |
| Adds a command, flag, or API operation | minor |
| Fixes a bug, improves a message, updates dependencies | patch (`0.1.3` → `0.1.4`) |

## 4. Update the version and changelog

1. Set `version` in `Cargo.toml`, then run `cargo check` so `Cargo.lock` follows.
2. In `CHANGELOG.md`, rename `## Unreleased` to `## <version> - <YYYY-MM-DD>`
   and add a new empty `## Unreleased` above it. dist publishes that section as
   the release notes, so write bullets for users, not commit subjects.
3. Check that dist sees it: `dist plan` lists `announcing v<version>` and the
   artifacts.

## 5. Verify, commit, tag

```bash
cargo fmt --check && cargo clippy --all-targets --locked -- -D warnings && cargo test --locked
git commit -am "Release <version>"
git push
git tag -a v<version> -m "visor <version>"
git push origin v<version>
```

## 6. Watch the release

```bash
gh run list --workflow Release --limit 1
gh run watch <run-id> --exit-status
```

Every job must pass, including `publish-homebrew-formula`. If that job fails
with a permission error, the `HOMEBREW_TAP_TOKEN` secret expired or lost write
access to `Visor-Finance/homebrew-tap`; ask the user to renew it with
`gh secret set HOMEBREW_TAP_TOKEN`, then rerun the failed job with
`gh run rerun <run-id> --failed`.

## 7. Verify the install

```bash
gh release view v<version> --json assets -q '.assets[].name'
brew update && brew upgrade visor-finance/tap/visor || brew install visor-finance/tap/visor
visor --version                 # must print <version>
```

## 8. Report

Give the user the release URL, the version, the bump reason, and the result of
step 7. If the release adds a command or changes behavior, mention that the
CLI page in `Visor-Finance/visor` (`developer-docs/cli.mdx` and
`developer-docs/pt-BR/cli.mdx`) may need the same update.
